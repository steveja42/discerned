# Corpus sweep — incident history and reasoning

How to actually RUN the sweep, the `-Backup`/`-Resume`/`-Attended` rules, the review loop, and the verdict/severity conventions all live in the **`corpus-sweep` project skill** (`.claude/skills/corpus-sweep/skill.md`) — read that first.

This file exists for one purpose: to hold the measured incidents and reasoning behind non-obvious rules in the sweep, so a future change doesn't quietly re-introduce a bug that was already found and fixed. Read a section here when a rule needs justifying, a sweep behaves unexpectedly, or you're about to touch the code a past incident is about. Domain count is whatever `tests/fixtures/corpus-domains.json` holds at the time — it changes as sites are added or dropped, and any count quoted below is as-measured on that date's corpus.

## Verdicts

**Verdicts judge the capture pipeline, not the site's access posture** (stated in the skill; the reasoning is here). A login wall, paywall, or gate the site itself chose to show is not a pipeline defect if it was faithfully captured — that's `clean`. Only a defect in handling content that *was* on the loaded page (wrong block, collapsed layout, dropped byline) earns `flaw`/`critical`. `blocked` is its own verdict with no severity, for when nothing was captured at all.

**Severity replaced a computed composite that was measured anti-predictive.** Against 203 scored-and-reviewed domains it scored AUC 0.445 — below the 0.5 coin-flip line — with 1 of its worst-10 actually bad against a 36.9% base rate, and 47 of 75 bad clips scoring ≤0.02. Every individual heuristic sat at chance (0.46-0.54); domains with no flags were bad at exactly the base rate. The cause was structural: the defects that matter are semantic (`apnews` scored 0.005 with no flags while capturing a video rail instead of the article), and no text-length ratio or gap-pixel count can see them. The raw diagnostics (`textCoverage`, `blankRatio`, `aspectDistorted`, `chromeHits`) survive as context for a reviewer already looking at the image; they are not a ranking on their own.

**A verdict must never describe a stale image.** `visual-findings.json` is one long-lived file, never recreated per run. Measured 2026-09-09: of 206 live verdicts, 113 were substantive-looking notes that in fact described an already-replaced image, indistinguishable from a fresh verdict by reading the text alone. `review-queue.mjs` now applies a per-surface staleness rule (stated in the skill) and prunes automatically. Both clauses of that rule are load-bearing: on a later 209-domain run, 208 of 209 images differed from the baseline (a sweep changes nearly everything) while only a handful of verdicts predated their capture — the image test alone would prune nearly the whole corpus, the timestamp test alone would keep verdicts describing replaced pictures.

Traps hit while building that rule, each a real defect at the time:
- **Never use mtime for staleness.** A sweep rewrites every PNG whether or not the capture changed; an mtime test queued 209 of 209 domains after any re-run. Compare image content against the baseline instead.
- **`where` is the defect location, not coverage.** A reviewer routinely reads both surfaces and names the one with the problem — `where=cast` appeared on both flaws and cleans. Reading it as "which surfaces were reviewed" wrongly re-queued clips, and a `widenWhere` helper built on that misreading rewrote `where` and prefixed notes, mangling a verdict across four runs. Coverage lives only in `clipReviewedAt`/`castReviewedAt`.
- **A single-surface review must not erase the other's stamp**, or it reads downstream as "never reviewed."
- **Slices go stale independently of the images.** Review reads the bands in `slices/`, not the raw PNGs. A domain re-captured outside the normal slicing path kept its old bands beside a fresh PNG with nothing flagging it — measured 2026-09-23, one domain's slices were 92h older than its clip while it wasn't even in the pending queue. The catch-up is now `slice-clip.py --all --stale-only` (an mtime compare — acceptable here because it can cause a spurious re-slice but never a missed one, the opposite asymmetry from verdict staleness).

**Timestamps in `visual-findings.json` are local time with a UTC offset** (RFC 3339, e.g. `2026-09-17T12:04:01.816-07:00`), not `Z`. A UTC stamp read beside a local file mtime inverts the comparison that decides staleness — a domain reviewed at 12:04 local and re-captured at 15:27 local shows UTC stamps (19:04, 22:27) that read as though the review came later. `Date.parse` yields the same instant either way; mixed-offset strings do not sort correctly as plain text, so never sort them as strings.

**Verifying a backup, not just the live run.** `review-queue.mjs`, `record-verdict.mjs`, and `slice-clip.py` all accept `--run-dir <folder>` to point at a backup's own images and findings, isolated from the live run. This matters because the gallery's REGRESSED tier requires BOTH sides of a comparison to carry a `reviewedAt` stamp, and a freshly-taken backup otherwise inherits only a handful of stamped entries. Verify a backup once with the same tools used on a live run and future regression detection becomes real instead of falling into the weaker `recheck` tier.

## Backups

**Backups are opt-in and five are kept, because of one measured loss.** A backup used to be taken automatically on every non-resume run (`SWEEP_BACKUP_KEEP=2`) — but a sweep is re-run far more often than it completes (failed preflight, burnt IP, wrong flag), and each re-run rotated a good baseline out and replaced it with a copy of the run that had just failed. On 2026-09-15 a cast regression could not be demonstrated because both surviving backups were taken 37 minutes apart, and had to be filed `regression: "unknown"`. Retention is `SWEEP_BACKUP_KEEP` (default 5, ~850 MB each) — a working week, the window in which a regression is actually noticed.

## The gallery's regression ranking

**A skip is not a regression.** A skip means the page never loaded (bot wall, 403, rate limit, dead URL) — it says nothing about the clipping pipeline. Skipped domains sort below every real capture change. Without this rule, the 2026-09-08 burnt-IP session buried five genuine regressions under seven walls that appeared that evening.

**Verdict changes have two confidence tiers**, because a prior run's verdicts are real review but of mixed reliability. A change where BOTH sides carry a `reviewedAt` stamp is a true `REGRESSED` (rank 0); a change against an unstamped baseline entry is a `recheck` (rank 1) — it may be a real regression or a baseline verdict that was simply wrong. Measured: 31 domains flipped clean→flaw against one baseline, and the two clean→critical among them were baseline errors, not regressions. Gating unstamped entries out discards usable verdicts; treating them as equal manufactures phantom regressions.

**`httpStatus` is recorded on every capture, success or skip**, because page text alone cannot separate the cases that matter when a domain is walled: 403 (site refuses us), 429 (our IP is rate-limited — recoverable), 503 (interstitial), 200 (a challenge served with a success code, which is also the tell for a captured-but-bogus page).

## Anti-detection and IP reputation

**Every observable wait is jittered**, not just the domain gap. Cloudflare's Bot Management scores behavior, not only rate — a metronomic interval fingerprints as automation even at a low overall rate. This applies to the post-navigation paint wait, the gate-poll loop, the press-and-hold gesture, and the between-domain gap (±35% jitter). `SWEEP_NO_JITTER=1` exists only to reproduce a timing-sensitive bug — never use it for a real run.

**Watch the IP's whole-session budget.** On 2026-09-08, a 14-domain defended-only retry pass degraded the exit IP until Google itself served an "unusual activity" captcha, after which every Cloudflare site failed regardless of the site. Treat a Google captcha mid-session as a hard stop — results after it measure the IP, not the sites. Cap defended domains at 3-5 per session; the full sweep is safer than a retry pass precisely because those domains are interleaved among the ordinary ones. See `[memory: project_ip_reputation_burns_globally]`.

**A Google-search referrer does not beat the walls** (measured 2026-09-06, `google-referral-probe.spec.ts`, `GREF=1`) — identical wall, identical byte counts, whether reached via a clicked result or a bare `goto`. The first "proof" it worked was a measurement bug: a selector also matched Google's own account-panel chrome, so the page never actually left google.com and a SERP was scored as content. Any future navigation-shape experiment must assert the landed host before classifying.

**A walled domain usually just needs `cf_clearance` banked by hand** — open it in the warm profile, clear the challenge, close Chrome, then re-run; the cookie is in the shared jar. Cookies are shared across every launch of the profile, so a warm-up performed mid-investigation silently changes the variable under test — before crediting a code change for a pass, check the cookie's `creation_utc` against the run's `ranAt`. Diagnose a gate with bare `curl -sI -A '<real UA>' <url>` first — a 403 with `Cf-Mitigated: challenge` proves the wall is the site's posture toward the IP, not the harness. Cloudflare challenges can be intermittent (a site 403'd, then 200'd on the identical URL two minutes later) — expect a residue of hard-walled domains every run and mark those `blocked` rather than chasing them. See `[memory: project_sweep_wall_is_cumulative_not_per_site]`.

**`SWEEP_GAP` (default 20s) exists because an unpaced run gets Cloudflare challenges on the last few sites while earlier ones loaded fine** — a block is not recoverable in-run, so pacing matters more than throughput. Medium in particular blocks on a second load in quick succession and then stays blocked across headed/headless and referrer variations until cleared by hand.

## Sweep-triage probes — causes actually found

Domain rebrands where a regex could never match again; changed article-ID schemes; a wrong hub URL returning an empty shell (mistaken for a paywall); `minText` rejecting image-wrapped 0-char anchors; a `display:flex` rule collapsing a comment thread. See the probe table in the skill for which probe answers which question.
