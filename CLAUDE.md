# CLAUDE.md — Discerned Monorepo Root

This is the parent workspace for the Discerned project. Use this folder when a question or task spans more than one sub-project.

## Repo shape

This is a **pnpm monorepo** at `github.com/steveja42/discerned`. It was migrated from two standalone repos (`discerned-ext` and `discerned-web`) via `git subtree`, so the full history of both is preserved under their respective prefixes. The old standalone repos are archived on GitHub and point at this one.

## Cross-project Conventions

- **Shared types** live in `discerned-ext/src/shared/types.ts` and are mirrored (not imported) into `discerned-web/lib/types.ts`. Keep them in sync manually.
- **Nostr tag conventions** (`online.discerned.interest`, etc.) are defined in `discerned-ext/src/shared/nostr/events.ts` — the web app's parser at `discerned-web/lib/nostr/parse.ts` must match them exactly.
- **Client version stamp.** Every published cast carries the NIP-89 tag `['client', 'discerned', '<version>']`; `tag[1]` stays `'discerned'` (that's what other Nostr clients read), the version is the third element. Casts are permanent and public, so this is the only way to know after the fact which capture pipeline produced a given event. The version is **injected**, not read from `chrome.runtime.getManifest()` inside `events.ts`: the factory stays pure (runs under jsdom in Vitest) and the committed golden fixtures in `tests/fixtures/events/` are generated from it — reading the live manifest would rewrite all ~20 on every version bump. Fixtures therefore carry the stable `DEFAULT_CLIENT_VERSION` (`0.0.0-dev`) placeholder; `background.ts` calls `setClientVersion(chrome.runtime.getManifest().version)` at **module scope**, so it re-applies on every MV3 service-worker wakeup (a listener-only assignment would leave the placeholder after a restart). Kind-30078 (private encrypted clips, not currently published) deliberately does **not** carry the version — its tags are public and kept minimal. Bump the version in three files together: `discerned-ext/manifest.json`, `discerned-ext/package.json`, `discerned-web/package.json`.
- **Click-to-play video** spans both projects. The extension emits a play card — `<a class="tweet-video" href="<canonical post URL>">` wrapping the poster, built in a site tagger's `postClone` — and the web app swaps it for a provider `<iframe>` on click (`discerned-web/lib/video-embed.ts` resolves the embed URL; `components/clips/ClipVideoPlayers.tsx` performs the swap). **Video bytes are never stored**: platform CDNs serve them behind expiring signed tokens and a `blob:` MSE source dies with the tab, so a clip keeps only a poster plus the canonical URL. Nothing is requested from the provider until the viewer clicks. Three constraints are load-bearing: (1) a cross-origin iframe is **destroyed by detaching it**, so the clip body is memoized (`ClipHtmlBody`) — a re-render that re-attaches the same element restarts playback from zero; (2) the swap must **hide** the poster card and insert the player beside it, never `replaceWith` it, because those cards live inside `dangerouslySetInnerHTML` and React throws `removeChild: node is not a child of this node` on its next reconcile (worse on casts, which ReactMarkdown reconciles more aggressively); (3) the live-player registry is a `useRef` keyed by **item id**, or switching items re-inserts one item's playing iframe into another. Snapchat is deliberately absent from the provider table — it sends `X-Frame-Options: DENY`.
- **Pipeline census.** Every article capture logs one line naming the element counts after each mutating stage (`clone → postClone → removeMarked → stripChrome → videoPosters → preSanitise → sanitised`, as `Ni/Nv/Na/Np` for img/video/anchor/picture). Dev builds only, tree-shaken from production. **Read it first when a clip is missing content** — it names the stage, which is otherwise guessed: a missing Snapchat avatar survived five wrong fixes aimed at the tagger before the census showed `removeGenericChrome` taking `9i/8a → 1i/1a`.
- **Extension ↔ web bridge** messages are typed in `discerned-ext/src/shared/types.ts` (`WebBridgeOutbound` / `WebBridgeInbound`) and consumed in `discerned-web/lib/bridge/extension-bridge.ts`. Clip bodies (`bodyHtml`, `thumbnail`) are **not** included in the bulk `DISCERNED_BRIDGE_CLIPS` message — they are fetched per-clip on demand via `DISCERNED_REQUEST_CLIP_BODY` / `DISCERNED_BRIDGE_CLIP_BODY` to stay under `chrome.runtime.sendMessage`'s 64 MiB hard limit. See `discerned-ext/CLAUDE.md` → Web-bridge protocol for details.
- **Default relays** are defined in `discerned-ext/src/shared/types.ts` (`DEFAULT_RELAYS`) and mirrored in `discerned-web/lib/constants.ts` — keep them in sync.
- **User relay preferences (NIP-65).** The effective relay set is **user-owned**: `getEffectiveRelays()` in `discerned-ext/src/shared/relays.ts` resolves it as `(mode defaults ∪ STORAGE_KEYS.USER_RELAYS) − STORAGE_KEYS.REMOVED_RELAYS`. Two invariants: **local mode is exclusive** (returns `[LOCAL_RELAY]` and ignores the user list, so dev/test casts never reach the public network) and the result is **never empty** (removals that would empty it fall back to the mode defaults). `REMOVED_RELAYS` is a separate list rather than a deletion so re-discovery can't resurrect a relay the user dropped. Every relay consumer goes through this one helper — publish, profile fetch, `naddr`/`nprofile` hints, the overlay's relay count. On sign-in (all three auth modes) `discoverAndMergeRelays` in `background.ts` fetches the identity's kind-10002 write relays via `background/relay-list-fetcher.ts` (24h per-pubkey cache; `window.nostr.getRelays()` is a nip07-only fallback) and merges them in. The **web app's Settings → Relays** section is the only editing UI; the extension remains the canonical store and syncs both ways over `DISCERNED_BRIDGE_RELAY_LIST` / `DISCERNED_SET_RELAY_LIST`. The overlay shows the list read-only. `RelayRow` + `normaliseRelayUrl` are mirrored (not imported) in `discerned-web/lib/constants.ts` — keep in sync.
- **Active relays vs default relays.** `DEFAULT_RELAYS` is the production wss:// list (mirrored ext↔web, keep in sync). The relay **mode** (`local` | `production`) is what's **deliberately not** mirrored — each side resolves it via its own platform idiom: the **extension** uses the `__DISCERNED_DEV_BUILD__` build flag (dev/test → `[ws://localhost:7777]`, production → `DEFAULT_RELAYS`, tree-shaken), while the **web app** uses the `NEXT_PUBLIC_LOCAL_RELAY` env var (set in `discerned-web/.env.local`, unset in production). In dev/test the local relay **replaces** the public ones so test casts never hit the real network. Publish ACK threshold is derived per-publish from the relays actually attempted via `minAcksFor()` (1 local, 2 production, capped at 2 however many the user adds). Run the relay with `pnpm relay:local` — see `tools/nostr-relay/README.md`.
- **Feedback deep link.** The extension's overlay Settings drawer opens the web app's `/feedback` page via an `OPEN_FEEDBACK` message (typed in `discerned-ext/src/shared/types.ts`, handled in `background.ts` by `openFeedbackTab` → the shared `openWebAppTab` helper). The URL carries `?target=extension&v=<manifest version>` and **deliberately nothing else** — reports become PUBLIC GitHub issues, so auth mode and publish mode are withheld rather than disclosed without the user's say-so. Don't "helpfully" add them. The page reads its params from `window.location.search` in a lazy `useState` initialiser, **not** `useSearchParams` (which forces a Suspense boundary under static export) and, unlike `TopBar`'s `?settings=1`, does not strip them — they're form state, so stripping would lose the prefill on reload.
- **Icons are generated across both projects by one script.** `discerned-ext/scripts/gen-icons.mjs` (`pnpm gen:icons`, run from `discerned-ext/`) rasterises SVG masters in `art/` into the extension's `public/icons/*.png`, the mirrored web copies that back the Nostr avatar, and the web app's `app/favicon.ico` / `app/icon.svg` / `app/apple-icon.png`. Deliberate **theme split**: azure for the extension + Nostr avatar, navy for the site's own favicons — so `discerned-web/public/icons/` is *not* a byte-mirror of the site favicon. All icons are transparent and full-bleed (no background tile, mark scaled to its tight bbox), and 16px uses a separate simplified master because the full mark is illegible at that size. All outputs are committed. After changing icons, re-run `pnpm pack:ext` too. Details in `discerned-ext/CLAUDE.md` → Icon assets.
- **Extension ID.** The extension is live on the Chrome Web Store at `https://chromewebstore.google.com/detail/discerned/gpfeknmodijdlehpnkfannklhplmfoma` — store ID **`gpfeknmodijdlehpnkfannklhplmfoma`**, now in `ALLOWED_ORIGINS` in `discerned-web/netlify/functions/feedback.mts`. `manifest.json` carries the **store's own public key** in `key`, so every local build (dev `dist/`, test `dist-test/`) installs under the store ID and therefore shares the store build's IndexedDB (`discerned`) instead of getting a separate one. CWS **rejects an uploaded package carrying a `key`**, so `manifestFor()` in `vite.config.ts` strips it for `mode === 'production'` only — i.e. `pnpm build` / `pnpm pack:ext`, the only builds ever uploaded. Don't strip it anywhere else, and don't hand-delete it from `manifest.json`: that silently un-pins the dev ID and orphans the clips again. **Chrome refuses to load two extensions with the same ID**, so the store build must be uninstalled while an unpacked build is loaded (and vice versa) — it swaps, it does not merge. The old pinned ID was `egocpdhpffaddnhjimclgabdhpbjbhod` (private `.pem` outside the repo at `~/.discerned-keys/discerned-ext.pem`); the `.pem` is now only of historical interest, since the pin comes from the store's key. The public key can be recovered from an installed store build at `extensions.settings.<id>.manifest.key` in the browser profile's `Secure Preferences` (the installed `manifest.json` does not contain it); verify any candidate by SHA-256 → first 16 bytes → hex digits mapped `0-f` to `a-p`, which must equal the store ID.
- **Extension permissions.** The extension requests **no broad host permission**: `host_permissions` is just `https://platform.twitter.com/*` (embedded-tweet extraction), with `<all_urls>` moved to `optional_host_permissions`. `content.ts` / `nip07-bridge.ts` are injected per tab on the toolbar-click / context-menu gesture under `activeTab` rather than declared in `content_scripts`. Three consequences that bite outside the extension folder. (1) **There is no test-only manifest** — specs run against the shipped one. Playwright cannot click the toolbar icon, so they press the extension's **keyboard command** (`discerned-activate`, Alt+Shift+Y) over CDP, which Chrome treats as a trusted gesture and which grants `activeTab` identically. **Any spec that navigates and then posts `__DISCERNED_TEST_CAPTURE` must first call `activateExtensionOnTab(ctx, url)`** (`tests/e2e/helpers/activateExtension.ts`) or it fails with "capture timeout"; `runFixtureVisual` does this for the specs that share it, and the corpus sweep + live `*-visual` specs are **not yet audited** for it. (2) The injected scripts are built by a **second Vite pass** into fixed-name IIFEs because `chrome.scripting.executeScript` runs classic scripts, not modules; under `vite dev` they are declared with an unreachable match instead so crxjs emits HMR-connected loaders. (3) Image inlining requires the optional grant; without it clips hotlink images instead of embedding them (a canvas fallback was tried and removed — see the sub-project doc). The grant can only be requested from an extension page (`src/permissions/`), never the overlay — `chrome.permissions` is not exposed to content scripts. Full detail in `discerned-ext/CLAUDE.md` → Permissions and on-demand injection, and → Running the e2e tests.
- **Install path.** Public installs go through the Web Store; the web app's `/get-extension` side-load page was **removed**. Every "Get the extension" CTA (`discerned-web/app/about/page.tsx`, `components/clips/LibraryEmpty.tsx`, `lib/marketing-copy.tsx`) links to `WEB_STORE_URL` in `discerned-web/lib/constants.ts`. `pnpm pack:ext` and the committed `discerned-web/public/discerned-extension.zip` are kept for side-loading (testers, pre-store builds) but are no longer linked from the site.

#### Running the fortnightly corpus sweep

The full 206-domain sweep is driven by `scripts/corpus-sweep-run.ps1`, not by invoking the spec directly. Use `powershell -ExecutionPolicy Bypass -File` — **`pwsh` is not installed on this machine**.

```powershell
# 1. Start it. Preflights, captures in the BACKGROUND, and starts a SECOND
#    hidden process that slices each domain's clip+cast top band the moment it
#    lands (batched — see below) and logs it to test-output/sweep-slices.log.
#
#    -Backup snapshots the PREVIOUS run first, giving this one something to be
#    compared against. It is OPT-IN: pass it when starting a real sweep, and
#    OMIT it when re-running after an error, or the good baseline is rotated
#    out and replaced by a copy of the failed run.
powershell -ExecutionPolicy Bypass -File scripts/corpus-sweep-run.ps1 -Backup

# 2. Hand this to Claude WHILE the sweep runs — this is the parallel half, and
#    it is not scriptable past this point: it means a model actually reading
#    every clip and cast slice and judging it.
#      "A corpus sweep is running in the background. Tail
#       test-output/sweep-slices.log (or Monitor it) and, as each domain is
#       announced, read its clip AND cast slice and record a verdict via
#       record-verdict.mjs. Call out real regressions explicitly
#       (regression:"regressed" + regressedFrom) where you can compare
#       against the previous backup. Keep going until the log prints DONE."

# 3. When it finishes, recover whatever was blocked — a SHORT, wider-paced pass.
#    Its own review queue is pre-sliced too (see corpus-sweep-run.ps1 -Foreground).
powershell -ExecutionPolicy Bypass -File scripts/corpus-sweep-run.ps1 -Resume -Gap 45 -Foreground

# 3b. ATTENDED recovery — for gates only a human can clear. Opens each domain in
#     a visible window and waits; close the tab to skip one you can't get past.
#     Requires -Only, never takes a backup, and runs corpus-sweep-manual (NOT
#     corpus-sweep with SWEEP_UNATTENDED unset — a different spec, see below).
powershell -ExecutionPolicy Bypass -File scripts/corpus-sweep-run.ps1 -Attended -Only discogs,producthunt

# 4. Rebuild the gallery, then diff against the backup the run took in step 1.
node tests/e2e/tools/sweep-gallery.mjs
node tests/e2e/tools/diff-sweep-run.mjs corpus-sweep-run--backup-<stamp>
```

**Every verdict carries a 0-10 severity.** The `verdict` field is three coarse buckets; `severity` is the magnitude inside them, and it is the number the gallery badges and sorts on now that the computed composite is gone. `record-verdict.mjs` **requires** it for `flaw`/`critical` (a defect with no magnitude cannot be prioritised or trended), defaults it to `0` for `clean`, and omits it for `blocked` — nothing was captured, so there is nothing to rate. It also rejects a severity that contradicts its verdict (`clean` 0-2, `flaw` 3-7, `critical` 6-10): a "flaw" rated 0 is a typo, not a judgment, and silently accepting it would poison the only real ranking. The scale, in one line each: **0** perfect · **1-2** cosmetic · **3-4** a real but minor loss (one missing byline, a dropped caption) · **5-6** a substantive piece wrong or missing but still recognisably the right content · **7-8** the clip misrepresents the page (wrong block, most of the body absent, layout collapsed) · **9-10** unusable (empty, or entirely the wrong content). Rate what you **see** in the image, not what you infer about the cause, and rate the worst of clip/cast — `where` already records which surface. Usage: `node tests/e2e/tools/record-verdict.mjs imdb flaw clip "Cast list missing." --severity 4`, or a `"severity"` key per entry in `--batch`.

**A verdict must never describe a stale image.** `visual-findings.json` is one long-lived file, never recreated per run — a domain re-captured by a new sweep leaves its OLD verdict sitting there untouched unless someone re-reviews it, with nothing marking it as describing a replaced image. Measured 2026-09-09: of 206 live verdicts, 113 were substantive-looking notes that in fact described an already-replaced image — indistinguishable from a fresh verdict by reading the text alone. Rule: a verdict survives a new run **only if its clip and cast images are byte-identical** to what they were reviewed against; run `node tests/e2e/tools/prune-stale-findings.mjs <baseline-folder>` (add `--dry-run` to preview) after a sweep to delete every verdict whose image changed, leaving `review-queue.mjs`'s pending count free of the "has a real note but describes yesterday's picture" ambiguity.

**Backups are OPT-IN (`-Backup`) and five are kept.** Both settings exist because of one measured loss. A backup used to be taken automatically on every non-resume run, with `SWEEP_BACKUP_KEEP=2` — but a sweep is re-run far more often than it completes (a failed preflight, a burnt IP, a wrong flag), and each re-run rotated a *good* baseline out and replaced it with a copy of the run that had just failed. On 2026-09-15 `snapchat-web`'s cast was reported working on 09-12 and was 9/10 critical, yet both surviving backups were taken 37 minutes apart on 09-14, so the regression could not be demonstrated and had to be filed `regression: "unknown"`. Pass `-Backup` when starting a sweep you intend to compare against; omit it when re-running after an error. Retention is `SWEEP_BACKUP_KEEP` (default 5, ~850 MB each) — a working week, which is the window in which a regression is actually noticed.

**Verifying a BACKUP, not just the live run.** `review-queue.mjs`, `record-verdict.mjs`, and `slice-clip.py` all accept `--run-dir <folder>` (or `$SWEEP_RUN_DIR`) to point at a backup folder's own images and its own `visual-findings.json`, completely isolated from the live `corpus-sweep-run/`. This matters because regression detection is only as good as the baseline: the "REGRESSED" tier in the gallery's sort requires BOTH sides of a comparison to carry a `reviewedAt` stamp, and a freshly-taken backup inherits whatever verdicts its source run had — which, before this was added, meant at most a handful of stamped entries. Verify the backup once with the same tools used on a live run (`node tests/e2e/tools/review-queue.mjs --run-dir <backup-folder>`, slice and record against it the same way) and every future sweep's regression detection becomes real instead of falling into the weaker `recheck` tier.

**There is no single command that runs the sweep AND visually verifies everything** — the verification step is a model reading images and writing judgment, which is inherently not scriptable the way capture and scoring are. What IS scripted is everything mechanical up to that point: preflight, backup, background capture, and — critically — **live slicing**, so by the time a domain is announced its clip and cast are already legible 1:1 images (`test-output/corpus-sweep-run/slices/`), not raw ~8000px PNGs that downscale ~4x and unreadable on read. `watch-sweep-stream.mjs` is the piece that makes "review in parallel with capture" literally true: it emits one line per landed domain (`Monitor`-friendly — no polling) and slices in batches of `SLICE_BATCH` (default 5) using `tools/slice-clip.py` (a plain Pillow crop — no browser, ~0.3s per domain; an earlier Chromium-based version paid a browser-launch cost that batching existed to amortize, which no longer applies but is kept anyway since it groups log output).

**The gallery's "regressions" sort ranks capture changes, and a SKIP IS NOT ONE.** A skip means the page never loaded (bot wall, 403, rate-limited IP, dead URL), so it says nothing about the clipping pipeline; skipped domains get a muted "didn't load (was ok)" pill and sort *below* every real capture change. Without that rule the 2026-09-08 burnt-IP session buried five genuine regressions under seven walls that appeared that evening. The ranking is: **verdict change first** (a judgment about the clip), then **whether the clip image changed at all**. It used to fall back to a computed `composite` score; that number was **removed** after being measured against 203 scored-and-reviewed domains and found *anti-predictive* — AUC 0.445 (below the 0.5 coin-flip line), 1 of its worst-10 was actually bad against a 36.9% base rate, and 47 of 75 bad clips scored ≤0.02. Every individual heuristic sat at chance (0.46–0.54) and domains with **no** flags were bad at exactly the base rate, so the flags carried no information at all. The cause was structural rather than a tuning problem: the defects that matter are semantic (`apnews` scored 0.005 with no flags while capturing a video rail instead of the article), and no text-length ratio or gap-pixel count can see them. What survives is the raw diagnostics (`textCoverage`, `blankRatio`, `aspectDistorted`, `chromeHits`) as **context for a reviewer already looking at the image**, plus the new reviewed **severity** (below). Verdict changes come in **two confidence tiers**, because a prior run's verdicts are real review but of mixed reliability — `visual-findings.json` says so itself: *"AI review has produced confident, specific notes that did not match the image … An existing verdict is NOT evidence a person looked."* A change where **both** sides carry a `reviewedAt` stamp is a true `REGRESSED` (rank 0); a change against an **unstamped** baseline entry is a `recheck` (rank 1) — open the image, since it may be a review-standard difference *or* a baseline verdict that was simply wrong. Measured: 31 domains flip clean→flaw against the 2026-08-30 baseline, and the two clean→**critical** among them (`apnews`, `lastfm`) were baseline errors, not regressions. Gating unstamped entries out discards 206 usable verdicts; treating them as equal manufactures 31 phantom regressions. Baseline selection is the most recent backup whose sidecars mostly share one 24h window, shown in the toolbar; `SWEEP_BASELINE=<folder>` overrides.

**Every capture records the navigation's `httpStatus`** in its `--score.json` (added 2026-09-08, on success as well as on skips). The page TEXT alone cannot separate the cases that matter when a domain is walled: **403** the site refuses us, **429** *our IP* is rate-limited (recoverable, not a site property), **503** a Cloudflare interstitial, **200** a challenge served with a success code. Without it, "still blocked" is ambiguous between "this site refuses us" and "we burnt the IP" — the question that could not be answered after the 2026-09-08 session. A 200 on a capture that scored oddly is also the tell for a captured-but-bogus page.

**Every observable wait is jittered, not just the domain gap.** Cloudflare's Bot Management scores *behaviour*, not only rate: a request firing at an exact interval (every 2.000s, every 3.500s) fingerprints as automation even when the overall rate is low. `jitterMs(base, jitter)` returns `base + Math.random() * jitter` and every wait a remote site can observe goes through it — the post-navigation paint wait, the gate-poll loop, and the press-and-hold gesture (pre-press pause, hold duration, post-release settle) in **both** sweep specs. The between-domain gap has its own ±35% jitter in `paceBeforeDomain`. Localhost waits (the `/clips` render) are deliberately left fixed — nothing there is watching. `SWEEP_NO_JITTER=1` restores fixed timing for reproducing a timing-sensitive bug; never use it for a real run. This matters most inside the gate-poll loop, which runs *while a challenge page is watching* — the one place a metronome is measured by the system being waited on.

**Watch the IP's whole-session budget.** Retrying the walled set back-to-back is the worst possible batch: on 2026-09-08 a 14-domain defended-only pass degraded the exit IP until **Google itself served an "unusual activity" captcha**, after which every Cloudflare site failed regardless of the site. Treat a Google captcha as a **hard stop** — results after it measure the IP, not the sites, so don't record `blocked` verdicts from that window (librarything captured earlier in the same session and failed later). Cap defended domains at 3-5 per session and spread the rest across days; the full sweep is safer than the retry pass precisely because those domains are interleaved among ~190 ordinary ones. See [memory: project_ip_reputation_burns_globally].

**Arriving via a Google search result does NOT beat the walls** (measured 2026-09-06). `gotoViaGoogle()` in the sweep and `tests/e2e/tools/google-referral-probe.spec.ts` (`GREF=1 --project=google-referral-probe`) exist to test this; the probe runs both paths per domain in one session and prints them side by side. Result for politico / medium-generic / discogs: **identical wall, identical byte counts**, whether reached by a clicked Google result or a bare `goto`. No domain is marked `"google": true` as a result. Keep the probe — it is the cheap way to re-test the hypothesis when a site's behaviour changes.

**The measurement trap that made this look true first time.** A selector of `a[href*="<host>"]:visible` also matches Google's own chrome — on a signed-in profile it hit the **account panel**, opened an overlay, and the page never left google.com. The classifier then read the SERP's own text, found no wall signature, and reported CONTENT for all 11 domains; the sweep, wired the same way, captured a Google results page for `medium-generic` ("People also ask", "Read more" snippet) and scored it `ok`. Both call sites now scope to `#search`/`#rso` **and assert the landed host is the target** before classifying, treating "still on google.com" as an explicit NO-CLICK. Any future navigation-shape experiment needs that assertion, or a failed click silently reads as a pass.

Four things make this cheaper than driving the spec by hand:

- **Capture and review overlap.** The sweep writes each domain's three PNGs + `score.json` the moment that domain finishes, so reviewing starts within minutes instead of after the whole run. `review-queue.mjs` lists only what is captured-but-unreviewed (**changed captures first** — it md5s each clip against the most recent backup, so the domains with something new to look at lead; a byte-identical clip whose verdict is merely stale can wait) and prints image paths — never image bytes — so the review loop stays token-cheap. A verdict is *stale* when its PNG is newer than its `reviewedAt` stamp, which is how a re-captured domain gets re-reviewed instead of keeping a verdict describing the old image.
- **`SWEEP_RESUME=1` makes recovery short.** It drops domains already captured `ok` and revisits only the failures. This is not just speed: **run length is itself the bot signal**, so a full 206-domain re-run to retry 30 blocked domains re-blocks the very domains it exists to recover. `SWEEP_RESUME_MAX_AGE_H` (default 96) bounds staleness; the run prints how many it reused vs re-ran, and warns when most artifacts have aged out (which would silently make a "resume" a full run).
- **Preflight catches the three failures that waste an hour**: Chrome still running (it holds the Profile 3 lock), a missing/stale `dist-test/`, and a dead web app on :3000.
- **`-Stop` aborts safely.** It kills Chrome plus *only* playwright-owned node processes. Never blanket-kill node — that takes down the always-running `pnpm dev` watchers, and the only symptom is a later preflight claiming the web app was never started.

`SWEEP_UNATTENDED=1` is set by the script for the automated passes: a full run has dozens of gated domains, and stopping for clicks is what turns two hours into a day. Domains that genuinely need a human click are recovered afterwards via `--project=corpus-sweep-manual`, wrapped as **`-Attended -Only <domains>`** (which adds the same preflight and post-run slicing, and refuses to run without `-Only` or alongside `-Resume`). Reach for the attended pass rather than un-setting `SWEEP_UNATTENDED` on the automated one: they are different specs, and `corpus-sweep`'s gate wait tops out at 20 polls whoever is watching. In the attended pass a `skipReason` of **"tab closed by user before the gate cleared" is a deliberate user action** — the documented escape hatch for a gate you can't clear — not a timeout or a script defect; it costs nothing beyond the time already spent, and the run moves straight on.

**A walled domain usually just needs `cf_clearance` banked by hand.** The warm profile carries clearance for ~20 hosts and none for the domains that keep failing — and the sweep cannot solve a challenge the profile has never cleared. So: open the domain by hand in that profile, clear the challenge, close Chrome, then run the attended pass; the cookie is in the shared jar and the sweep inherits it. Measured 2026-09-13 — discogs and producthunt both 403'd the attended run, were visited by hand (writing `cf_clearance` at 00:45:42 and 00:48:45, *after* the 00:43/00:44 failures), and cleared thereafter. Note this does **not** contradict the `gotoViaGoogle` finding below: the referrer is not the mechanism, a real interaction solving the challenge is. **Cookies are shared across every launch of the profile, so a warm-up performed mid-investigation silently changes the variable under test** — before crediting any code-level change for a pass, compare the run's `ranAt` against `select host_key,name,creation_utc from cookies` in `Profile 3/Network/Cookies` (`creation_utc` is microseconds since 1601-01-01). A "no-extension control" here returned 200 and was nearly reported as proof the extension caused the wall; it only proved the cookie now existed.

**Diagnose a gate with bare `curl` before blaming the harness.** `curl -sI -A '<real UA>' <url>` involves no Playwright, no extension and no profile, so a `403` with `Cf-Mitigated: challenge` proves the wall is the site's posture toward your IP rather than anything the sweep does — and hitting `https://www.google.com/` in the same breath separates "this site is walling us" from the burnt-IP state in [memory: project_ip_reputation_burns_globally]. Measured 2026-09-13: discogs served `403 Cf-Mitigated: challenge` to bare curl, then **200 on the identical URL ~2 minutes later** and four times running, so its challenge is an intermittent window, not a durable block — while boardgamegeek and lemmy.world challenged even their own homepages. Worth knowing before spending a session warming profiles: the warm `Profile 3` is genuinely warm (~4.5 MB of history, ~5,900 cookies) and already carries `cf_clearance` for ~20 hosts, but has none for discogs / boardgamegeek / lemmy.world, which is the actual gap for those three. Expect a residue of hard-walled domains every run — mark those `blocked` rather than chasing them, and see [memory: project_sweep_wall_is_cumulative_not_per_site] before treating a block as a property of the site.

#### Sweep-triage probes

Three diagnostics that answer the questions a corpus-sweep score *can't*. All are opt-in, write to `test-output/`, and are **diagnostics, not gates** — the pixel baselines remain the regression floor. Reach for these before writing a capture fix: a sweep finding rarely means what it looks like, and guessing the mechanism has produced wrong fixes more than once.

| Probe | Answers | Run |
|---|---|---|
| `tools/finder-diag-probe.spec.ts` | **Two modes.** *finder* (default): which content-block the layout finder picks and why — tag/class/textLen/visLen/area/linkRatio/#p/#img per candidate, plus whether the real body text is even in the DOM. Distinguishes a finder mis-pick from a bot-gate/lazy-load. Also reports the **headline relationship** — where the page `<h1>` sits relative to BOTH the finder's winner and the tier-1 root, and whether it survived into the capture. That distinction matters: Tier 1 runs first and often wins a tighter root, so `inWinner=true` does not mean the headline was captured. *picker* (`DIAG_MODE=picker`): why a discovery seed reported "no link matched picker" — final URL, `<title>`, anchor/regex/minText counts, real deep links, screenshot, verdict. | `DIAG=1 [DIAG_MODE=picker] [DIAG_ONLY=a,b] [DIAG_HEADED=1] [DIAG_WAIT=60] [DIAG_GAP=45] --project=finder-diag-probe` |
| `tools/hidden-prose-probe.spec.ts` | Is low text-coverage a **paywall** (prose in the DOM but `visibility:hidden` — capture is faithful, do NOT "fix" it) or a **finder mis-pick** (prose visible, wrong block won)? Reports visible-vs-hidden prose counts, what hid each paragraph, and where the visible prose lives. | `HIDDEN=1 [HIDDEN_ONLY=folha] [HIDDEN_HEADED=1] --project=hidden-prose-probe` |
| `tools/clip-width-probe.spec.ts` | Why a rendered clip **collapses into narrow columns** (text one character per line). Renders a saved capture through the real `.clip-body` CSS and reports the narrowest text elements + the ancestor chain that set the width, plus a table/cell census (a collapsed table's CELLS are narrow while the table is not). Works **offline from a saved HTML file**, so a fix can be iterated without re-hitting a Cloudflare-gated site. **Pass `CLIPW_WIDTH=610`** — it otherwise renders at the 1280px viewport, while the sweep's column is ~610px, and a ribbon only collapses when the column is too narrow for it. | `CLIPW=1 CLIPW_DOMAIN=<d> [CLIPW_WIDTH=610] [CLIPW_HTML=<path>] --project=clip-width-probe` |
| `tools/pre-ws-probe.spec.ts` | Why a code block loses its **whitespace** (`apiVersion:v1kind:Pod`) or gains it (`apiVersion : v1`). Reports, per `<pre>` on the live page, whether whitespace text nodes exist, how many, and what the line wrappers compute to. Settles the one question the markup can't be reasoned about: syntax highlighters wrap every run of whitespace in its OWN element (Chroma, Pygments: `<span class="w"> </span>`), so the whitespace is present but deletable — which named `collapseEmpty` after two wrong fixes had been built against `applyFlexSeparation`. | `PREWS=1 [PREWS_URL=<url>] --project=pre-ws-probe` |
| `tools/flaky-capture-probe.spec.ts` | Is a domain's capture **actually flaky, or deterministically broken**? Loads the page ONCE (clear any gate by hand) and captures N times against that same settled DOM, printing the pipeline census and page-text length for each. Politico looked like a 2-in-5 flake across sweep runs; this made it **8 of 8** and the census named the stage. Re-measures the page each round, so a DOM that changed between captures can't be mistaken for pipeline non-determinism. | `FLAKY=1 FLAKY_URL=<url> [FLAKY_N=8] [FLAKY_WAIT=180] --project=flaky-capture-probe` |

Notes:
- **Picker mode reads its seeds from `discover-article-urls.spec.ts`** rather than keeping a second copy — an earlier standalone probe drifted to a stale hub URL and silently probed the wrong page.
- `DIAG_GAP` paces between sites. Hitting ~10 domains back-to-back from one IP is itself a bot signal: an unpaced run got Cloudflare challenges on the *last* three sites while earlier ones loaded fine. **The corpus sweep has the same defence as `SWEEP_GAP` (default 20s, `0` disables).** It defaults ON because a block is not recoverable in-run: a `ray id` / "blocked by network security" page is a HARD signature, which the Pass-2 headed retry deliberately will not retry, so the domain is lost for the run. **Medium blocks on a second load in quick succession** and then stays blocked for that profile across headed/headless and referrer variations until cleared by hand — so sites whose corpus note says HEADED must never take a headless hit first (see `CLOUDFLARE_HEADED_SITES`). Prefer offline fixture baselines when verifying a pipeline change; re-sweep live only when you need the verdict.
- Chrome must be **fully closed** before any of these run — they use the warm `Profile 3`, and a live Chrome holds the profile lock (`launchPersistentContext` fails).
- Causes these have actually found: domain rebrands (`msnbc.com` → `ms.now`, `phys.org` → `techxplore.com`) where the regex can never match; changed article-ID schemes (CBC `-1.N` → `-9.N`); wrong hub URL returning an empty shell (mistaken for a paywall); `minText` rejecting image-wrapped 0-char anchors; and `.dx-stats` (`display:flex`) collapsing a comment thread.
- `tests/e2e/tagger-canary.spec.ts` — opt-in (`CANARY=1`, `--project=tagger-canary`) weekly canary that runs each per-site tagger's selector-anchor manifest against the LIVE site and fails naming the exact dead selector when a redesign breaks a tagger (page-load flakes are SKIPs, not fails). A tagger may have several targets when the site has distinct page shapes (primal: profile feed + thread) — see `discerned-ext/CLAUDE.md` for why the manifest groups variants while the *targets* split them. Scheduled locally via `scripts/tagger-canary-local.ps1` (warm `test` Chrome profile → covers CF-walled Reddit/YouTube/StackOverflow) and in CI via `.github/workflows/tagger-canary.yml` (open sites only — the warm profile is gitignored, so CI silently gets an empty one). See `discerned-ext/CLAUDE.md` → "Tagger canary / repair loop".

### Dev-mode test bridge
Production-code edits in `discerned-ext/src/content/content.ts` add a message listener gated on `__DISCERNED_DEV_BUILD__` (a Vite `define` flag set to `true` only for `--mode test` / `--mode development`). It accepts `__DISCERNED_TEST_CAPTURE`, `__DISCERNED_TEST_CLIP`, and `__DISCERNED_TEST_CAST` messages so Playwright can drive `captureContext()`, the CLIP path, and the CAST **build** path without the manual evaluation overlay. Production builds tree-shake this code out entirely.

`__DISCERNED_TEST_CAST` runs the extension's REAL cast pipeline without signing or publishing: the content script does the real `deriveLongFormMarkdown` (turndown needs the content-script DOM the SW lacks), then the background's test-only `BUILD_CAST` handler runs the real `buildCastTemplates` (`buildShortNote` + `createLongFormEvent`) and returns the unsigned kind-1 + kind-30023 templates. Specs sign them with a throwaway key and render through `/discerns`. This drives production code — not a reimplementation — so the cast the visual specs screenshot is byte-for-byte what `handleCast` would publish. (Note: persistent test profiles cache the extension's MV3 service worker across a `pnpm build:test`, so a new background handler like `BUILD_CAST` can 404 with a stale SW — `launchWithExtension` now clears the SW/Code-Cache dirs for named profiles on launch to force a re-register.)

### dist vs dist-test vs dist-pack isolation
- `dist/` — dev build, written incrementally by `pnpm dev`. Loaded by your Brave browser for daily use.
- `dist-test/` — test build (`pnpm build:test`). Loaded by Playwright. **E2E tests never touch your dev install.**
- `dist-pack/` — production build (`pnpm build`, also what `pnpm pack:ext` zips). Never touches `dist/`, so a production build can't collide with or clobber the live dev output.

## Deployment

The web app is deployed by **Netlify** from `github.com/steveja42/discerned` on every push to `main` (when files under `discerned-web/` change — guarded by a bare `ignore = "..."` string under `[build]`; note a `[build.ignore]` *table* is rejected by Netlify). Config lives in both:
- `netlify.toml` at workspace root (the fallback)
- `discerned-web/netlify.toml` (read when Netlify's "package path" is set to `discerned-web` in the dashboard)

Both pin `NODE_VERSION = "22"` and `PNPM_VERSION = "11"`. Node 22 is required by pnpm 11 (uses `node:sqlite`). Build command is `pnpm install --frozen-lockfile && pnpm --filter=./discerned-web build`, publish dir is `discerned-web/out` (a static export — `next.config.ts` sets `output: 'export'`, so nothing is emitted to `.next/` for deploy).

**Netlify Functions.** `discerned-web/netlify/functions/` holds the only server-side code in the project (the static export rules out Next API routes and server actions). Currently one function: `feedback.mts`, which turns a `/feedback` submission into a GitHub issue. The directory **must** stay under `discerned-web/` — the `ignore` rule above would skip the deploy for a function-only change otherwise. Functions are ESM bundled by esbuild at deploy time, not by Next, so they carry their own `tsconfig.json` (`allowImportingTsExtensions`) and the app tsconfig excludes them; `pnpm type-check` checks both. Secrets (`TURNSTILE_SECRET_KEY`, `GITHUB_FEEDBACK_TOKEN`) live only in the Netlify dashboard and are never `NEXT_PUBLIC_`-prefixed — that prefix would inline them into the client bundle.
